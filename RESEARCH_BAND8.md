# Band-8: простой DND, Recorder и отзывы о Watch 5

16 ноября 2026 года. Журналы, фотографии экранов и идентификаторы устройств в публичные исходники не входят.

## Отзывы о band-7

- REDMI Watch 6: владелец подтвердил подключение и работу NFC.
- Watch S5: подключение подтверждено; NFC — предварительный отзыв. Незашифрованных карт для проверки нет, копирование ключей не подтверждено.
- Watch 5: новый отзыв и скриншот подтверждают ошибку синхронизации при показанном подключении в смарт-режиме. Причина из скриншота неизвестна.

В прежнем журнале Watch 5 o61w был DualCoreWearOSDeviceModel. Google WatchApi существовал, но getWatchByPeerId возвращал null, а FaceWearOsHelperImpl завершал синхронизацию с getWearOSWatch == null. BLE-подключение карточки устройства само по себе не подтверждает готовность Wear OS SDK. Новый отзыв без журнала нельзя автоматически приписывать той же причине.

В band-8 путь Watch 5 не меняется вслепую. Нужен свежий «Журнал приложения» владельца: начать запись, воспроизвести ошибку синхронизации, открыть циферблаты, остановить и сохранить; отправить в личные сообщения. Нужны модель, прошивка и версия Android. Сброс устройства и перепривязка для сбора журнала не требуются. Подключённый для нашей проверки Samsung SM-S711B не является телефоном владельца проблемного Watch 5.

## Исправление простого DND

Для устройств без capability V3 bit 0x4 простой режим отправлял manual_zen_rule через syncZenRule, то есть использовал протокол правил, поддержку которых устройство не заявляет. Исправление межпроцессного переключателя в band-5 не устраняло эту проблему.

В 3.60.0i найден штатный ZenUtils.postSyncZenMode: type=2, subtype=23, System/DoNotDisturb, status=0 при включённом DND телефона и 2 при выключенном. Назначение команды и значения совпадают с независимо описанным протоколом Gadgetbridge:

- https://github.com/Freeyourgadget/Gadgetbridge/blob/master/app/src/main/proto/xiaomi.proto
- https://github.com/Freeyourgadget/Gadgetbridge/blob/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/xiaomi/services/XiaomiSystemService.java

Простой режим теперь использует именно эту штатную команду, адресованную выбранному did, без изменения расписаний/правил. Устройства с битом 0x4 сохраняют прежний путь правил. Wear OS исключён, переключатель остаётся выключенным по умолчанию. Штатная настройка синхронизации DND на устройстве не подменяется.

До подтверждения транспортом состояние не считается подтверждённым. Отказ делает его неизвестным и допускает следующую отправку; ответ старого запроса не перезаписывает новый. Смена устройства или выключение переключателя инвалидируют ответы. Новый журнал MOD различает queued, transport acknowledged и transport error; идентификаторы не выводятся. Подтверждение транспорта ещё не доказывает изменение значка DND на самом браслете.

Локальные тесты: структура реального создаваемого запроса ON/OFF и состояния подтверждения/отказа, быстрый переход к противоположному состоянию, устаревший и повторный callback, смена устройства и выключение переключателя. Для утверждения «DND на SB 10 работает» нужна проверка владельцем SB 10 с журналом включения и выключения. На нашем SB 11 простой режим не применяется, поскольку устройство поддерживает правила.

## Recorder: что показал разбор прошивок

Сопоставлены полные q66gl 4.200.078 и q66cn 4.100.179. Это разные ветки и даты; сравнение ограничено найденными структурами. Чтение выполнено локально, образы не менялись.

Адресное отображение строк 0x2C0C0000 независимо совпало для 25 различных имён приложений в каждом образе. В китайском AP найдена запись по смещению 0xB9D0C0: com.xiaomi.miwear.recorder, /resource/app/recorder/launcher.bin и указатель кода 0x0C604A71. Код этой функции передаёт каталог ресурсов общему загрузчику. В глобальном AP пакет встречается в двух общих участках кода, но аналогичной записи приложения не найдено. Наличие строк интерфейса и общих функций поэтому не доказывает, что штатный Recorder зарегистрирован и может быть включён телефоном.

На устройстве ранее возвращались 28 приложений без Recorder; эксперимент с CAPABILITY_SUPPORT_SYNC_TO_RECORDER 0x40000 не помог и после перезагрузки. В кандидате band-8 эксперимент выключен.

При этом строка system.record есть в обоих AP-образах. Xiaomi документирует API Vela записи и воспроизведения:

- https://iot.mi.com/vela/quickapp/en/features/system/record.html
- https://iot.mi.com/vela/quickapp/en/features/other/audio.html

В таблице поддержки API нет подтверждения для Smart Band 11. Строка в образе тоже не доказывает рабочий backend. Подготовлен отдельный RPK-пробник com.markus.recorderprobe: загрузка модулей при открытии, запись WAV 3 секунды только по кнопке, ручное воспроизведение, остановка при выходе и ограничение ожидания ответа. Сети и фоновой записи нет. Это проверка альтернативного приложения, а не найденный переключатель штатного диктофона. Успех SDK/полученный URI ещё требует проверки слышимой записи.

Пробник: aiot-toolkit 2.0.5, SHA-256 da17c904b29588d541756f0c4a4a6e5fa518c65f7f085fd13300e17be362a497, 13562 байта. Наличие только system.record/system.audio в manifest проверено. Установка и запись допустимы только с отдельного разрешения владельца; прошивка не отправляется.

Установлен с разрешения владельца через adb install -r; Android compile -m verify успешно. ## Пробы записи на браслете

Владелец отдельно разрешил установку RPK. Версия 0.1.0 установилась, но API не был доступен пробнику. В 0.1.1 проверен статический импорт по документации и default-экспорт: владелец получил «Модуль не найден / start: нет модуля». Эти сообщения сформированы самим пробником при отсутствии объекта API; это не текст ошибки прошивки.

Подготовлена и установлена 0.1.2, versionCode 3, 13847 байт, SHA-256 9828232477064a87be22a8f004c121a40810f9084908d860a680c377c96b7d9e. Она дополнительно сравнивает наличие system.record/system.audio/system.device; getInfo, getSerial и getDeviceId не вызываются. Контроль стандартных модулей исключает общий отказ загрузки API: владелец сообщил record: нет, audio: нет, device: function. Стандартный system.device доступен, а объекты system.record и system.audio пробнику не предоставлены. Доступного документированного пути записи для этого RPK на данной прошивке не найдено. Это не доказывает полного отсутствия низкоуровневого аудиокода, но включением признака телефона или этим RPK штатный диктофон не восстановлен. После завершения пробы SDK подтвердил удаление com.markus.recorderprobe. Автоматической записи не было, работающий аудиофайл не получен. На браслет передавался только отдельно разрешённый RPK, прошивка не менялась. Исходная настройка удержания экрана телефона восстановлена в 0.
